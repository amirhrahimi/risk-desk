# ADR-025 Pending orders (phase P5): Set Pending, Del Pending, the overlay and moving an order by its line

- **Context:** P5 adds OP-07 Set Pending, OP-08 Del Pending, the pending order overlay (F-22) and OP-16 on top of the P2 gateway (G-02, G-05, G-07 and G-08 existed and had passed GatewaySmoke on A1–A6) and the P4 planning lines and Pending Info. Implementing it left points open: how the overlay and a user's drag of its line must not fight each other, which caps apply to a moved order that was not placed by RiskDesk or whose risk does not grow, what BC-10 means for a pending order on a netting account (06 OP-07 does not say; 03 BC-10 speaks of "a new order"), and how the self-test reads an order's expiration without `#ifdef` in App code. The test runs also showed that every unattended MT4 start added a copy of the owner's chart to the terminal's profile.
- **Decision:**
  - Files outside the CLAUDE.md §4 layout (split like ADR-019/021/022): `App/CommandsPending.mqh` (OP-07, OP-08, OP-16; part of `CCommands`), `App/ControllerOverlay.mqh` (overlay refresh and drops; part of `CController`), `App/UiSelfTestPending.mqh` + `UiSelfTestPendingMove.mqh` (debug only), `build/profile-guard.ps1`. `UI/PendingOverlay.mqh` is the layout's file.
  - **Overlay (F-22):** App lists the orders in chart scope every refresh (G-07; MT5 stop-limit orders are not drawn, RiskDesk does not modify them) and writes the label texts (BC-05 valuation, recomputed only when the orders or the account changed); `CPendingOverlay` draws them. A line is moved only when its order's value changed (MetaTrader's own trade levels, another tool, a modify) or after a drop, so the user's drag is never pulled back while it is in progress; the drop arrives as `CHARTEVENT_OBJECT_DRAG` (also on MT4). A change in the properties dialog (`CHARTEVENT_OBJECT_CHANGE`) counts as a move only when the price changed. Labels use the overlay line's colour and the planning labels' font, size and placement (05 §5, ADR-024, through `CLines::LabelSpot`). Objects of an order that is no longer listed are removed; the first refresh after `OnInit` also removes objects of orders that went while RiskDesk was not running and those of the old symbol. A deleted overlay object is drawn again on the next refresh. `InpShowPendingOverlay=false` removes everything.
  - **OP-16 caps** (`CRiskBudget::CheckMove`, unit-tested): a move that does not raise the order's risk is always allowed, so an order above a cap can still be tightened and moving the entry (same distance) needs no budget (D29). Otherwise the per-trade cap applies to every order, and the total cap with the old contribution replaced (04 §5) to RiskDesk orders that count towards the open risk; other orders are checked per trade only. An order without SL is not moved, since its risk is unknown (D28). A line dropped at the order's own price changes nothing (amber). After every drop the overlay shows the order as it is on the server: the new values, or the old ones when the move was refused (snap back).
  - **Set Pending** follows Buy/Sell's order of checks (ADR-022) with entry = the Entry line: permissions, spec, quote, Risk %, lines, classification and BC-07 (04 §7), BC-05, netting, MT5 volume limit, lots, caps, margin at the entry price (F-31, although most servers reserve margin only at the fill), confirmations, G-02 (BC-06 pending ladder, BC-08 expiration ladder, SL verified, rule R7). The status names the expiry when one was set. The order count limit (BC-09) is checked by G-02 before sending.
  - **Netting (BC-10) for pending orders (D27):** a pending order in the position's direction merges with it when it fills and its SL/TP replace the position's: it is checked against the caps as the merged position (averaged open at the order's entry, the order's SL) and always confirmed. An opposite one would reduce or reverse the position when it fills: refused unless `InpNettingAllowOpposite`, then confirmed.
  - **Del Pending:** tickets are collected first, then G-05 each (freeze level checked by the gateway); MT5 stop-limit orders are included (06 OP-08). An order that went in between (filled or deleted elsewhere) turns the status amber, so a fill is not missed; failures are listed with their reason. The screenshot carries the ticket when one order was deleted, else 0 (D30).
  - `SOrder.expiration` (new field, both gateways) holds the order's expiry; the overlay entry tooltip shows it and the self-test checks it (T-23).
  - **G-05 waits for the terminal's list** (found on A4, Dukascopy MT4): `OrderDelete` returned OK while the terminal kept listing the deleted order for a moment, so the overlay still drew it and a second Del Pending sent a delete that MetaTrader itself answered 4108 "unknown ticket" (or "invalid request"), a red status for an order that was gone. Both gateways now wait after a successful delete until the terminal no longer lists the ticket (at most about 2 s), and a delete that fails for a ticket the terminal then drops counts as "already gone" (amber, 06 §3), not as a failure.
  - **Debug pending suite** (`run-uitest.ps1 -Suite pending`, 08 §3f): real pending orders on demo accounts only (R13), placed 3 SL distances away so they do not fill, magic 772288, a second symbol for T-15, every test order deleted again. The panel suite clicks Set Pending only after removing the pending lines and Del Pending only when no order is in its scope, so it still never trades.
  - **Terminal profile guard:** MT4 keeps the chart of a startup configuration as a temporary chart (`start.tpl`: `temp_chart=1`) that takes a chart-file number at close without removing the file that had it, so each unattended start added one more copy of the owner's chart (the P4 growth to 74 charts had the same cause; the upper-case `.CHR` seen then was a symptom). `run-tests.ps1`, `run-script.ps1` and `run-uitest.ps1` now copy the active chart profile before starting the terminal and put it back after it closed (`build/profile-guard.ps1`); MT5, which did not show the problem, is guarded the same way.
- **Consequences:** T-13…T-15, T-23, T-39, F-22 and the pending part of T-08 run unattended on every demo account and symbol. RiskDesk now modifies a placed order when its overlay line is dropped (ADR-014, CLAUDE.md §1). The overlay costs one order list per refresh (a few orders, NFR-03); the money labels are valued only when an order or the balance changes. Unattended runs no longer change the owner's charts. 05 §6, 06 OP-07/OP-08/OP-16, 08 §3f and 11 D27–D31 updated.
